## Yoyu v1.7.0

**A second board you can actually buy and flash, and a setup page that walks
you through it.**

### Two boards, and the page asks which one first

The **ESP32-S3-Touch-AMOLED-2.16** stops being a build-it-from-source
curiosity. It flashes from the browser like the 2″ board does, updates itself
over the air, and the setup page offers it directly.

That required asking a question the page never used to ask — *which board is
this?* — before anything gets written to flash, because the image and the panel
have to match. So the page is now a wizard: five steps, one at a time, board
choice first.

The two boards are drawn to scale next to each other rather than described,
each showing its own default theme, because size and shape are the whole
decision and there is no photograph of the AMOLED to show you. Your choice
stays visible at the top of the flash step with a way to change it.

> **Touch still does not work on the AMOLED.** Its card on the setup page says
> so before you choose, not after you buy. The screen is a display, not a
> control: screens rotate on their own and everything else is set from a
> browser.

### The setup page is a guide now, not a reference

It used to put all three steps, every warning and every troubleshooting fold on
screen at once — a good reference, and a poor thing to follow. Now:

- **One step on screen at a time**, with a progress rail you can walk back
  through. Your place survives a reload, so unplugging the board and coming
  back doesn't start you over.
- **A closing step.** The photo of a working board is at the end, where it is a
  payoff, along with the two things everyone asks next: where the settings live,
  and how to stop leaving the companion running.
- **Advice that matches your board.** Tell it you have the AMOLED and it stops
  telling you to tap the screen.
- **Warnings where they apply.** The Chrome-and-Edge notice is a precondition of
  the flash step; past it, it disappears rather than sitting there as an
  instruction you can no longer act on.
- **Nothing lost without JavaScript.** Every step is still in the page in
  reading order — the wizard is an upgrade layered on top, not a replacement.

### A flasher that had no images to install

`manifest-amoled216.json` pointed at four firmware files the Pages build never
downloaded. Offering the AMOLED in the picker would have produced an Install
that 404s — which reads to a buyer as a broken board, not a broken deploy. Both
boards' images are bundled now, and the check that refuses to publish a flasher
lagging the current release runs **per board**: one correct image is no evidence
about the other.

### Two boards at once

Now that a second board is something you can buy and flash, owning both is an
ordinary setup — and it did not work. The companion stopped at the **first**
board that answered, so the second was never fed and sat there saying *waiting
for your computer*. Both are found and fed now, from a single read of your
usage.

- **A board has a permanent id.** `yoyu.local` was never an identity: the
  boards resolve the name collision themselves, so the second one to boot
  becomes `yoyu-2.local` — both reachable, but the assignment swaps when they
  restart together. Top-up keys used to be filed under whatever address you
  paired against, which with two boards could mean looking up one board's key
  for the other. They are filed under the board's own id now, and existing
  keys are re-filed automatically. It is printed at the bottom of the page the board
  serves at its own address.
- **A stale saved address no longer traps it.** A remembered address that
  stopped answering was still truthy, so discovery never ran a second time and
  the companion pushed into the void for as long as it ran. It now checks that
  what it remembers still answers, and goes looking if not.
- **A refused top-up key says so.** It used to fail silently and retry
  forever. The board is told apart from the key: a refusal drops the key and
  asks you to pair that board again.
- **The tray gives each board its own submenu** — open, settings, alerts,
  firmware, pair — plus **Look for boards** for when you add one. A single
  board keeps exactly the flat menu it had.

`--rescan` does the same from the command line.

### Touch, on the AMOLED

`0xD101` turned out to be the controller's **debug** mode, not the generic
"command mode" its name suggested. The info registers are only readable from
it, so the driver entered it to read the check code and then never left — and a
chip parked in debug mode answers every touch read with a frozen idle frame and
never raises its interrupt, which is exactly the symptom.

Normal reporting has to be asked for by name (`0xD109`), and the chip echoes the
mode it settled into, so the transition is checkable rather than hopeful. It now
reports `0x09` and the frames go from frozen to live.

**It still never reports a press.** The register semantics were wrong either
way and are now right, but the panel-to-controller link remains the suspect.
This is progress, not a fix.

### Upgrading

Over the air from `/update`, or re-flash from the setup page. Wi-Fi, login,
settings and history all survive.
