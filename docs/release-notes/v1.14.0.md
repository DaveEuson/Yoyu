## Yoyu v1.14.0

**A Pace screen that says whether you will run out before each window resets**,
and a setup page that shows you every screen and lets you pick which ones you
want.

### Pace

Claude's own usage panel has started saying things like *"At this pace you'll
run out Wednesday morning, before Thursday's reset."* The board now answers the
same question, on its own screen.

At the top is one line you can read from across the desk: `Weekly runs out` /
`Wed 9 AM`, or `On pace` / `for every reset` when nothing is in danger. Below
it is a row per window, with how much is used, a bar, and a tick marking where
an even pace would have you by now. If the fill is past the tick, you are
spending faster than the window lasts. Under each bar it says what that pace
comes to: when it runs out and how early, or roughly how much will be used at
the reset.

**How it works it out.** Anthropic's usage data carries no forecast, so this
is Yoyu's own calculation, made from what the board already knows: how much of
a window is used, and how far into the window we are.

- **The week is judged by your average since it started.** One busy afternoon
  says little about seven days.
- **The session is judged by the last hour.** Five hours is short enough that
  what you are doing now is what decides it.

It stays quiet when it has too little to go on. An hour into a session, or
half a day into a week, is the minimum before it will call anything; until
then a single busy minute would read as a runaway.

As a check, the weekly method was run against a real account that was 69% used,
three days and eighteen hours into its week. It came out at Wednesday morning,
before Thursday's reset, which is the same answer Claude's panel gave for the
same account. It is still our number rather than theirs, so the two can
disagree, most likely on the session, where "the last hour" is a choice.

If you have usage credits waiting, running out is where the cost starts rather
than a wall, and the screen says so instead of going red.

### Focus was getting this wrong

Focus already had a small projection for the session window. It took its rate
from the History buffer, which follows whichever window is tightest, so
whenever the weekly window was tighter than the session it subtracted one
window's numbers from the other's and called the result a burn rate.

Focus now uses the same calculation as Pace, so two screens can no longer
disagree about one window. It also projects the weekly window when there is no
session window to show, and prints days once a gap is longer than one.

### Choosing screens during setup

The setup page has a new step between Wi-Fi and the companion. Each screen is
shown as a small picture of itself next to a sentence about what it is for,
with a switch to keep it or leave it out. You can also choose which screen
comes first, and whether they change when you tap or on a timer.

A web page is not allowed to send anything to a device on your home network,
so the page cannot change the board itself. Instead it opens the board's own
settings page with your choices already ticked, and pressing **Save** there
keeps them. The link can suggest settings; it cannot change them.

It knows which board you picked in step 1. The AMOLED has no working touch, so
its screens default to changing every 20 seconds, and Actions says it needs a
touchscreen this board does not have.

The board's settings page has the same one-line descriptions under every
screen, so it is no longer a list of names you have to have tapped through to
understand.

### Nine screens

The board kept which screens were switched on in a single byte, with one bit
per screen, and there were already eight. A ninth needed a wider value and a
migration, not just another entry in a list.

Your existing choices carry over. Pace is switched on once, the way every
screen added since v1.4.0 has been, and stays off if you turn it off. The old
one-byte setting is still written as well, so a board rolled back to older
firmware keeps its first eight choices.

The on-device Settings list now fits nine rows. At the old spacing the ninth
landed on the hint line at the bottom of the screen.

### For checking

`/api/status` gains a `pace` array with what the screen would say about each
window, and the numbers behind it, so a projection that looks wrong on the
glass can be checked from a browser.

### The toolchain underneath moved

This release is built with Arduino core 3.x instead of 2.0.17, which the
firmware had been pinned to since the start. PlatformIO's official platform
never shipped core 3.x, so the build now comes from pioarduino, pinned to one
exact release.

Nothing about that is visible on the board, with one exception worth knowing
about. The update check parsed GitHub's answer as it arrived off the network.
GitHub sends that answer in pieces about half the time, and pieces are not
something the parser could read, so the check reported **"couldn't reach
GitHub"** for a check that had reached GitHub perfectly well and been told the
answer. The retry it has always done was hiding half of this. It reads the
whole answer first now.

If your board has ever claimed it could not reach GitHub while everything else
about it worked, that was probably this.

The move is also what makes a third, cheaper board possible later. Core 2.0.17
cannot build for the newer ESP32 chips at all.

### Upgrading

Over the air from `/update`, or re-flash from the setup page. Wi-Fi, login,
settings and history all survive.
